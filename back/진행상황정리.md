# QA 파일 관리 시스템 수정 진행상황 정리

## 1. 프로젝트 변경 요구사항

### 현재 구조
- 파일 업로드 시 즉시 DB에 저장 (QaFileInfo, QaFileSheet 엔티티 사용)
- H2 인메모리 DB 사용 (임시 개발용)

### 변경 목표
- 로컬 폴더 파일 관리: DB 저장 없이 메모리에서만 관리
- 파일 수정 후 HTML/JSONL 출력 파일 생성
- 체크박스로 선택한 파일만 외부 DB에 저장
- 로컬 폴더 목록과 DB 목록 분리 표시
- DB 저장된 파일 재수정 시 로컬 폴더로 복원

---

## 3. 최근 구현 사항 메모

- `/api/qa/workspace`는 폴더별 페이지 정보를 반환하도록 개선됨. 쿼리 파라미터 `afterPage`, `beforePage`, `devPage`(기본 0)와 `size`(기본 5, 최대 100)를 이용해 각 폴더의 페이지를 독립적으로 요청할 수 있음.
- 각 폴더 응답(`WorkspaceFolderResponse`)에는 `page`, `size`, `totalPages`, `totalElements`가 포함되어 프론트엔드가 `< 1 2 3 4 5 >` 형태의 페이지 네비게이션을 표시할 수 있음.
- JSONL 변환은 여전히 `/api/qa/convert/jsonl`을 사용하며, after 경로로 저장된 파일을 `/api/qa/files/after/promote`로 `C:\Dev\doc\jsonl`(현재 고정된 Dev 경로)로 이동시키는 구조임.
- `PredictionFileService` 추가: `/api/qa/files/json/split`은 predict(s) 배열을 찾아 HTML을 `before` 폴더에 저장하고, `/api/qa/files/json/merge`는 선택된 HTML을 순서대로 합쳐 JSON을 생성한 뒤 `after` 폴더에 저장·다운로드하도록 구현됨. 분할된 HTML에는 `data-predict-title`, `data-predict-body` 속성이 있어 병합 시 제목/본문을 그대로 복원할 수 있음.

## 2. 사수에게 확인해야 할 질문 목록

### 2.1 외부 DB 관련 질문

#### 질문 1: 외부 DB 정보
- **질문**: 외부 DB의 종류와 접속 정보를 알려줄 수 있나요? (MySQL, PostgreSQL, Oracle 등)
- **필요 정보**: 
  - DB 종류
  - 접속 URL
  - 사용자명/비밀번호
  - 데이터베이스명

#### 질문 2: 외부 DB 테이블 구조
- **질문**: 외부 DB에 이미 존재하는 테이블 구조를 알려줄 수 있나요?
- **필요 정보**:
  - 테이블명 (qa_file_info, qa_file_sheet 등)
  - 컬럼명 및 데이터 타입
  - PRIMARY KEY, FOREIGN KEY 제약조건
  - 필수 컬럼과 선택 컬럼 구분
  - 인덱스 정보

#### 질문 3: 외부 DB 저장 방식
- **질문**: 외부 DB에 저장할 때 어떤 방식으로 진행하면 되나요?
- **옵션**:
  - JPA Repository 사용 (엔티티 필요)
  - MyBatis Mapper 사용 (이미 pom.xml에 포함됨)
  - JdbcTemplate 직접 사용 (엔티티 불필요)
  - Native Query 사용

#### 질문 4: 원본 문서 경로 형식
- **질문**: 외부 DB에 저장되는 원본 문서의 경로 형식이 어떻게 되나요?
- **예시**: `/external/db/documents/file1.xlsx` 또는 다른 형식
- **필요 정보**: 경로 규칙, 기본 경로 설정 방법

#### 질문 5: DB 저장 시 저장 범위
- **질문**: 외부 DB에 저장할 때 어떤 데이터를 저장해야 하나요?
- **확인 필요**:
  - originalFilePath: 외부 DB의 원본 문서 경로
  - htmlFilePath: HTML 파일 경로
  - jsonlFilePath: JSONL 파일 경로
  - htmlContent: HTML 내용 전체를 CLOB로 저장?
  - jsonlContent: JSONL 내용 전체를 저장?
  - sheets 정보: 시트별 HTML 내용도 저장?

### 2.2 로컬 폴더 관리 관련 질문

#### 질문 6: 로컬 폴더 경로 관리
- **질문**: 로컬 폴더 경로는 어떻게 관리하면 되나요?
- **확인 필요**:
  - 사용자 PC의 실제 경로를 프론트엔드에서 전달받는지
  - 백엔드 설정 파일에 기본 경로를 지정하는지
  - 사용자별로 다른 경로를 사용하는지

#### 질문 7: 파일 접근 방식
- **질문**: 사용자 PC의 로컬 폴더에 있는 파일을 백엔드에서 직접 읽을 수 있나요?
- **확인 필요**:
  - 프론트엔드에서 파일을 읽어서 백엔드로 전달하는지
  - 백엔드가 파일 경로를 받아서 직접 읽는지
  - 파일 업로드 방식인지, 경로만 전달하는지

#### 질문 8: 출력 파일 저장 위치
- **질문**: 수정 완료된 HTML/JSONL 파일은 어디에 저장하나요?
- **확인 필요**:
  - 사용자 PC의 로컬 폴더에 저장 (프론트엔드에서 다운로드)
  - 서버의 특정 폴더에 저장
  - 저장 경로 규칙

### 2.3 Domain 엔티티 관련 질문

#### 질문 9: Domain 엔티티 사용 여부
- **질문**: 로컬 파일 관리와 외부 DB 저장 모두에서 Domain 엔티티(QaFileInfo, QaFileSheet)를 사용하지 않아도 되나요?
- **확인 필요**:
  - 로컬 파일 관리: 메모리 모델만 사용 가능한지
  - 외부 DB 저장: 엔티티 없이 JdbcTemplate/MyBatis로 직접 SQL 실행 가능한지
  - 또는 외부 DB 저장 시에만 엔티티 사용 가능한지

#### 질문 10: 기존 엔티티 처리
- **질문**: 현재 domain 패키지의 QaFileInfo, QaFileSheet 엔티티는 어떻게 처리하면 되나요?
- **옵션**:
  - 삭제하고 새로 만들기
  - 외부 DB 저장용으로만 사용
  - 유지하되 로컬 파일 관리에는 사용 안 함

### 2.4 파일 상태 관리 관련 질문

#### 질문 11: 파일 상태 값 정의
- **질문**: 파일 상태를 어떻게 구분하면 되나요?
- **확인 필요**:
  - "대기": 로컬 폴더에 있지만 아직 수정 안 함
  - "수정-완료": HTML/JSONL 파일 생성 완료, DB 저장 대기
  - "db적재-완료": DB에 저장 완료
  - "실패": 처리 중 오류 발생
  - 추가 상태 값이 필요한지

#### 질문 12: 완료된 파일 처리
- **질문**: DB 저장 완료된 파일을 로컬 폴더에서 어떻게 처리하나요?
- **확인 필요**:
  - 파일은 유지하고 목록에서만 제외
  - "완료된 폴더"로 이동
  - 파일 삭제

### 2.5 DB 목록 파일 재수정 관련 질문

#### 질문 13: 재수정 시 파일 복원 방식
- **질문**: DB 목록의 파일을 재수정할 때 어떻게 처리하면 되나요?
- **확인 필요**:
  - DB에서 HTML/JSONL 데이터를 가져와서 로컬 폴더에 파일로 생성
  - DB에 저장된 원본 문서 경로에서 원본 파일을 다시 가져오기
  - 어떤 방식이 적절한지

## 3. 현재까지 확인된 정보

### 3.1 프로젝트 흐름 (확인됨)
1. 파일 선택 (로컬 폴더 지정해서 자동으로 업로드) - 바로 HTML table 보이도록
2. 수정 후 JSONL, HTML 파일 출력 (컴퓨터에 있는 폴더에 저장)
3. 변경된 파일을 체크박스로 선택
4. 한꺼번에 지정된 DB에 저장하기
5. 로컬에 있는 폴더에 있는 파일들과 지정된 DB에 있는 파일 목록을 분리
6. 로컬에서 지정된 DB로 보낸 파일들은 로컬 폴더에서 안 보이고 지정된 DB 목록으로 이동
7. 지정된 DB 목록으로 이동된 파일을 재수정 시 다시 로컬 폴더로 이동 후 원래 진행순서 시작

### 3.2 로컬 폴더 관리 (확인됨)
- 로컬 폴더 경로: 사용자 PC의 실제 경로 (예: C:\Users\사용자\Documents\QA파일)
- 백엔드 설정 파일(application.yml)에 기본 경로 지정
- 프론트엔드에서 폴더를 스캔해서 파일 목록을 백엔드로 전달
- 파일명을 입력하면 시트 수정하는 화면이 나오도록

### 3.3 출력 파일 저장 (확인됨)
- 로컬폴더 안에 "출력파일" 폴더를 따로 만들어서 저장
- 구조: 로컬폴더/출력파일/
- 사용자 PC에 저장 (프론트엔드에서 다운로드 받아서 저장)

### 3.4 DB 저장 범위 (확인됨)
- originalFilePath, jsonlFilePath, htmlFilePath 저장
- 원본 문서는 외부 DB에 있을 예정
- 외부 DB는 운영계에 올라가있는 AI DB
- 이 부분은 일단 임시로 지정해서 넣으면 될 것 같음

### 3.5 파일 삭제/이동 (확인됨)
- 로컬 → DB 이동 시: 파일은 남기고 목록에서만 제외
- 완료된 파일은 "완료된 폴더"로 이동하는 방식

### 3.6 DB 목록 파일 재수정 (확인됨)
- DB에서 HTML/JSONL 데이터를 가져와서 로컬 폴더에 파일로 생성

### 3.7 파일 상태 (확인됨)
- 수정-완료, 대기(수정 후 db에 적재할 파일), db적재-완료, 실패
- 같은 파일이 로컬과 DB에 모두 있을 수 있음
- 나중에 DB에 있는 파일들로 학습을 시킬 건데, 해당 파일 중에 가장 최신 버전으로 학습하도록 로직 설정 예정

### 3.8 Domain 엔티티 (확인됨)
- 현재 domain에 있는 파일이 없는 채로 진행이 되어야 함
- 로컬 파일 관리는 domain 엔티티 없이 메모리 모델만 사용
- 외부 DB 저장 시에도 엔티티 사용이 안 된다면 JdbcTemplate/MyBatis로 직접 SQL 실행

## 4. 예상 답변에 따른 진행 방법

### 시나리오 A: 외부 DB 정보를 모두 받은 경우

#### 진행 방법
1. **설정 파일 수정**
   - application.yml에 외부 DB 접속 정보 추가
   - 로컬 폴더 기본 경로 설정

2. **메모리 모델 생성**
   - `model/LocalFileData.java` 생성 (엔티티 아님)
   - 로컬 파일 정보를 메모리에 저장

3. **로컬 파일 관리 서비스 생성**
   - `LocalFileStorageService.java` 생성
   - ConcurrentHashMap으로 메모리 관리
   - 파일 읽기, 변환, 상태 관리

4. **외부 DB 저장 서비스 생성**
   - `ExternalDbService.java` 생성
   - JdbcTemplate 또는 MyBatis로 직접 SQL 실행
   - 테이블 구조에 맞춰 INSERT 쿼리 작성

5. **API 수정/추가**
   - 로컬 파일 관리 API 추가 (DB 저장 없음)
   - 외부 DB 저장 API 추가
   - DB 목록 조회 API 추가

#### 사용 기술
- JdbcTemplate 또는 MyBatis
- 메모리 기반 저장 (ConcurrentHashMap)
- 파일 I/O (로컬 파일 읽기/쓰기)

### 시나리오 B: 외부 DB 정보를 일부만 받은 경우

#### 진행 방법
1. **임시 구조로 진행**
   - 외부 DB 테이블 구조를 임시로 가정
   - 기본적인 컬럼만 포함한 구조로 구현
   - 추후 실제 구조 확인 후 수정

2. **확장 가능한 구조로 설계**
   - DTO를 유연하게 설계
   - 컬럼 추가/수정이 쉽도록 구조화

3. **주석으로 표시**
   - 임시로 가정한 부분을 주석으로 명확히 표시
   - 실제 구조 확인 후 수정 필요 부분 표시

#### 사용 기술
- JdbcTemplate (유연한 SQL 작성)
- 설정 파일에 임시 값 명시

### 시나리오 C: Domain 엔티티를 사용해야 하는 경우

#### 진행 방법
1. **엔티티 수정**
   - QaFileInfo, QaFileSheet 엔티티를 외부 DB 테이블 구조에 맞춰 수정
   - @Table 어노테이션으로 외부 DB 테이블 매핑
   - ddl-auto: none 설정 (테이블 생성 안 함)

2. **Repository 사용**
   - QaFileInfoRepository는 외부 DB 저장용으로만 사용
   - 로컬 파일 관리에는 사용 안 함

3. **서비스 분리**
   - LocalFileStorageService: 메모리만 사용, 엔티티 사용 안 함
   - QaFileInfoService: 외부 DB 저장 시에만 엔티티 사용

#### 사용 기술
- JPA Repository
- 메모리 기반 저장 (로컬 파일 관리)
- 엔티티 기반 저장 (외부 DB 저장)

## 5. 진행하려고 했던 방식들

### 방식 1: 완전 메모리 기반 + JdbcTemplate (Domain 엔티티 없음)

#### 구조
```
로컬 파일 관리:
- LocalFileData (메모리 모델)
- LocalFileStorageService (ConcurrentHashMap 사용)
- DB 저장 없음

외부 DB 저장:
- ExternalDbService (JdbcTemplate 사용)
- 직접 SQL INSERT 실행
- Domain 엔티티 사용 안 함
```

#### 장점
- Domain 엔티티 완전 제거 가능
- 외부 DB 테이블 구조에 유연하게 대응
- JPA 제약 없이 SQL 직접 제어

#### 단점
- SQL을 직접 작성해야 함
- 타입 안정성이 약간 낮음

#### 구현 파일
- `model/LocalFileData.java`
- `service/LocalFileStorageService.java`
- `service/ExternalDbService.java` (JdbcTemplate)
- `dto/QaFileInfoDto.java` (DB 저장용 DTO)

### 방식 2: 메모리 기반 + MyBatis (Domain 엔티티 없음)

#### 구조
```
로컬 파일 관리:
- LocalFileData (메모리 모델)
- LocalFileStorageService (ConcurrentHashMap 사용)
- DB 저장 없음

외부 DB 저장:
- ExternalDbService (MyBatis Mapper 사용)
- SQL 매핑 파일 작성
- Domain 엔티티 사용 안 함
```

#### 장점
- SQL과 Java 코드 분리
- MyBatis가 이미 pom.xml에 포함됨
- 복잡한 쿼리 작성 용이

#### 단점
- MyBatis 설정 필요
- SQL 매핑 파일 작성 필요

#### 구현 파일
- `model/LocalFileData.java`
- `service/LocalFileStorageService.java`
- `service/ExternalDbService.java` (MyBatis)
- `mapper/QaFileInfoMapper.java`
- `mapper/QaFileInfoMapper.xml`

### 방식 3: 메모리 기반 + JPA Repository (Domain 엔티티 사용)

#### 구조
```
로컬 파일 관리:
- LocalFileData (메모리 모델)
- LocalFileStorageService (ConcurrentHashMap 사용)
- DB 저장 없음

외부 DB 저장:
- QaFileInfo, QaFileSheet 엔티티 사용
- QaFileInfoRepository 사용
- 외부 DB 테이블 구조에 맞춰 엔티티 수정
```

#### 장점
- JPA의 편의 기능 활용
- 타입 안정성
- 자동 매핑

#### 단점
